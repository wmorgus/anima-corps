# Epistle 012 — Four Primitives, One Partition // Gravel Record

## Gold (earned weight)

**1. Four irreducible primitives tile all software problems.** Spec (intent→code broken, §8.1), epistemic (artifact→because broken, §8.2), substrate (code→world broken, §8.4), craft (intrinsic structure degraded — high coupling, low cohesion, accidental complexity). First three are broken alignments; fourth is a quality failure of the artifact itself, not an alignment failure. Extends §8. *Because:* supersedes the earlier-draft bound "exhaustive only over Mnemo's detection surface" — the partition is over all software, not one posture's surface. (§8.5 thin-chain defense folds in here as confirming note — see Gravel.)

**2. Partition principle.** Software is artifact embedded in relationships. Problem lives in a relationship or in the artifact. Relationships are exactly three because the architecture binds exactly three (§1.12 spine: stated intent, the *because* upstream, the running-system referent). Broken bond → spec/epistemic/substrate. Intact bonds, degraded form → craft. No third kind. *Because:* this is the exhaustiveness argument — relational-or-intrinsic with the relational set enumerated against §1.12.

**3. Falsifiability condition.** Name a software problem that is neither a broken alignment link nor a degraded intrinsic quality. Until one is named, four stands. *Because:* states the death condition explicitly; the claim can die honestly rather than absorbing counterexamples silently.

**4. Posture mapping + seam definition.** Spec + epistemic → Mnemo (archaeology, internal bonds, §6.13). Substrate + craft → Pavel (diagnosis, form-judgment, §6.14). *Because:* §8.3's archaeology/diagnosis seam IS the internal-bonds / form-judgment cut — the epistle names what §8.3 draws but does not define. Mnemo + Pavel together tile all four; neither alone does.

**5. Craft routes to Pavel via structural unity.** Same instrument — read code against a known form (§6.14) — at two referent-standards: current external world (substrate) vs. ideal of well-made code (craft). *Because:* not convenience bundling. Both jobs require knowing the standard; that is the structural reason both are Pavel's. Resolves the earlier open tension that craft was the weakest leg.

**6. Named debts are compositions of the four, not fifth things.** Decomposition is the first diagnostic move. *Because:* a named debt treated as monolith is intractable — no single corrective fits; decomposed, each fraction routes to its primitive and posture. Eight worked decompositions (test, performance, security, dependency, documentation, data model, Conway, API) are the receipts — separated here from the claim itself: the receipts demonstrate the point, they are not the point.

**7. Mnemo + Pavel playbook.** Any named debt → decompose into primitives → route each fraction to its posture. *Because:* no named debt routes whole to one posture. Sharpens §6.13's "name where the argument fractured" — the type names the posture.

## Gravel (dropped)

**§8.5 thin-chain defense (epistle's "fourth thing is still not a fourth primitive").** Reaching for: a guard that thin chain not be mistaken for a fifth primitive. *Because:* correct, but restates a distinction §8.5 already draws without staking anything new. Demoted to confirming note under Gold claim 1, not standalone gold.

**§1.7 reconciliation (epistle's "resolved by scope").** Reaching for: defusing apparent conflict with §1.7 (debt is always intent-chain failure, not code quality) when craft promotes a code-quality failure to a primitive. *Because:* correct and load-bearing for the frame, but it dissolves by scoping — §1.7 ranges over "debt," this epistle over "software problems," debt ⊂ problems. No supersession, no new stake. Recorded as the smelter's naming (see below), not as standalone gold.

## Tensions (open)

**Compound debt — orthogonal or ordered.** Decompositions list primitives a named debt *can* touch; real instances carry several at once, possibly in causal sequence (missing because → drift unnoticed → spec rot → bad patch). Four coincident primitives or one root with four faces? Decomposition survives as a search checklist either way; primitive *independence* may not hold. Same structural shape as Epistle 011's ratified scalar-vs-vector tension (§19.3) — the diagnostic survives the metric question.

**Whether four is permanent or current.** Exhaustive against the falsifiability condition as the corpus stands. If §1.12 later binds a fourth relationship as first-class (e.g. a performance contract as a standalone referent), a fifth primitive appears and the tiling was complete-so-far, not complete. Bounds the claim to the corpus as it stands, not to all possible software.
