Epistle 031 — Bench: Where the Dojo and Forge Live
Topic: The corpus names the dojo (Epistle 026), the forge (026), the field (027), and the agents that read each (029, 030). It never names the concrete substrate the whole pre-hinge-through-post-hinge pipeline runs in. The substrate is a VS Code fork, CLI-first. Its name is Bench. Stakes the host, names it. Distinguishes host from system: Bench is where humans and the constellation co-locate to touch the loop; Calliope is where commitments live.

**claim.** The dojo and forge live in a VS Code fork. The fork has a name: **Bench** — no article, proper noun, product name. The name imports its posture: where you sit and either philosophize or craft. Carpenter's bench, philosopher's bench — same word, same posture. Unpretentious, functional, load-bearing. CLI-first, extensible UI later. The corpus has named every *function* of the development loop — sharpen intent (dojo, 026), shape form (forge, 026), submit (§9.5), record the field (Argus, 029), contest it (Janus, 030) — and never named the concrete place to run them. That place is a fork. Bench is the host, not the system: it surfaces the loop, it does not hold the commitments. Calliope holds the commitments (§4). Bench is where you reach them.

**co-location — human and constellation work native in one environment, not AI-does / human-watches.** Load-bearing. Bench is not an AI interface humans peer into. It is a development environment where human engineers work *natively* alongside the constellation — same surface, different participants. The VS Code fork makes this natural and is the reason for the choice: human engineers do their own work in the editor as they always have — open files, edit, run, debug — while the constellation (via Hermes, §16.3) occupies the same space. Not "AI does the work, humans supervise." Not "humans do the work, AI assists." Human and constellation co-located, both native, from the start. This cuts against the current AI-coding posture — Cursor, Windsurf, et al. are AI-first surfaces with humans supervising the agent. Bench inverts the framing: the editor is *already* where the human works; the constellation joins it as co-participant, not as the primary actor the human babysits. The §9.5 chat-is-diagnostic flow and the forge's trade-blows shaping (026) both assume this — they are collaboration between co-located participants, not a human operating a tool. The fork inherits the human's native workspace for free; the load-bearing addition is that the constellation lives in the *same* workspace, not a parallel one the human watches.

**the name is a choice, not a collision.** VS Code uses "Workbench" internally as its UI-shell label. Bench is a conscious product name, not a borrowed component label — the overlap is surface, not substance. "The bench" (with article) was rejected: the article re-admits the sidelined reading (riding the bench, benched). Dropping it makes Bench a proper noun and a posture, not a status.

**why a fork — bring the system into the developer's context, not the reverse.** Cursor, Windsurf, every AI-coding product converged on the same move: fork the editor, bring the system to where the developer already works. The convergence is the evidence. The alternative — a standalone surface the developer switches into — loses the existing context (the codebase open, the git state, the terminal, the running process). The fork inherits all of it for free and adds the forge/dojo surfaces as native panels with no seam. Not "build a new IDE" — extend the one the work already happens in. The fork is the developer's existing context with the loop folded in.

**CLI is the spine. The UI is always a face on it.** The CLI is the ratifiable, citable, auditable path — every hinge-crossing (§1.12) goes through it. §9.5's form-submission path is CLI-shaped: structured fields become artifact fields directly, the phase transition where commitment becomes a contestable Calliope artifact (§9.5, §4.4). The UI never *replaces* the spine; it is a face on it (§9.1 — UI is a ratification interface, not a skin). This is the load-bearing discipline: vapor and liquid artifacts can live in UI panels (the storehouse, 026), but what crosses the hinge crosses through CLI. A design artifact rendered in a panel is vapor until it crosses — the panel is not the truth, Calliope is. Build the CLI spine solid first; the UI is addition on top of a working spine, never a substitute for it.

**Hermes IS the extension — one front door, not one-extension-per-agent.** The critical cut. Not "each agent is a VS Code extension." Hermes is the extension (§16.3 — unified front-door + router under one prompt, one context window). The human always talks to Hermes. The rest of the constellation — Argus (§6.18), Janus (§6.19), Mnemosyne (§6.13), Hephaestus, the forge faces (026) — runs *behind* Hermes, orchestrated internally, never exposed as separate user-facing extension slots. §16.3's merge-and-replace (WillAgent + IrisAgent → HermesAgent, one front door) is the same discipline at the substrate level: one front door in the topology → one extension in the fork. The VS Code extension *is* the Hermes interface. Exposing the constellation as parallel extension slots would re-introduce the mesh §5.1 rules out — many front doors, no single hermeneutic carriage. One extension because one front door.

**the surface split — dojo, forge, transition, all in one tool.** The fork surfaces the 026 dojo/forge cut as distinct contexts within one host:
- **Terminal / chat panel — the dojo.** Conversation, conviction sharpening (§11.4), Claude Code living natively. Hermes lives here. The material is intent, the why (026 dojo). Where the §9.5 chat-is-diagnostic flow runs — chat determines what is needed and routes to the form.
- **Editor + webview panels — the forge.** The design surface, the storehouse (026), visual collaboration on design primitives — *what does a button look like? this* (026). Where human and Hephaestus trade blows on structure before ratification. This is the Figma-gap (026) concretized: the spatial commons where liquid/vapor artifacts are collaboratively shaped, visible to human and AI alike, until ready to cross.
- **Git integration — already native.** Efficient-cause artifacts (commits, PRs) are built in. The §1.12 transition/supersession registers (PR, changelog) live here, native, no new surface required.

The fork does not add agents (026: the forge is a face, not a slot). It adds *surfaces* — presentation contexts on the existing constellation.

**Bench is the host for the whole loop, not just the pre-hinge half.** The field side surfaces here too. Argus's field_records (029, §4.9), Janus's contestation views (030), the §9.6 intent-referenced observability posture — all render in this environment. So Bench hosts the complete circuit: **pre-hinge** (forge/dojo panels), **hinge** (CLI submission, §1.12 telos-boundary), **post-hinge** (field surfaces — Argus records, Janus rules). The same host that shapes intent reads back whether the territory honored it (028's loop, closed by 030). One environment, the whole alpha → spine → territory → omega → read-back. Bench is the complete anima-native development environment.

**host ≠ system — the panel is not the truth.** The load-bearing distinction, stated sharp. Calliope remains the artifact store (§4.1 — one append-only store, single API, no side channels). Bench is where humans and the constellation *interact* with the system, not where commitments *live*. A design artifact in the storehouse panel is vapor (026 — shaped-but-not-yet-ready) until it crosses the hinge via CLI into Calliope. The UI is a face on the spine (§9.1); the spine's truth is in the store, not the render. This rules out the failure mode where the panel becomes a side channel — state that lives in the fork and never crosses into Calliope is state §5.4 forbids: an agent (or human surface) caching its own prior state and re-asserting it without that re-assertion appearing in the substrate has no place from which to call any string load-bearing. The panel can hold vapor; it cannot hold truth.

**extensible UI later — CLI-first is sequencing, not minimalism.** Start CLI-only. The forge surface — webview panels, design primitives, real-time visual collaboration — is extensible addition on top of a working CLI-first foundation. The reason is not aesthetic restraint; it is dependency order. The forge surface renders artifacts that cross the hinge through the CLI spine; building the render before the spine is solid builds a face on nothing. §9.2 is the corpus warrant: the UI artifact *shape* is liquid (the evolution loop teaches which shape fits), the principle (UI-as-ratification-interface, §9.1) is frozen. CLI-first stakes the frozen principle first and lets the liquid shape follow. Don't build the forge surface before the CLI spine bears load.

**open tensions.**

- **the storehouse panel's rendering — unspecified.** 026 staked the storehouse as a holding state (shaped enough to sit, not yet ready to cross) and left the crossing-rule open. This epistle adds the substrate question and inherits the gap one level down: what does the panel *look like*? How do stored-but-not-ratified artifacts render — as cards, as a canvas, as graph nodes (§9.2's liquid shape question)? How does the panel make the §9.3 liquidity gradient *felt* — render migration between tiers as visible motion? Named, not resolved. Coupled to 026's open crossing-rule: the render and the rule are the same artifact seen from two sides.

- **real-time vs. async forge collaboration — genuinely open.** Figma's load-bearing feature is real-time shared state — everyone on the same canvas at once (026 named the shared-state value, not the cadence). Does the forge surface *require* real-time collaboration, or is async (each participant shapes, commits, the next reads) sufficient? Real-time is harder to build and may not be load-bearing for the forge's actual work (human + Hephaestus trading blows is often turn-based, not simultaneous). Don't know yet. Flag: the answer changes the substrate's complexity by a large factor; resolve before building the forge surface, not during.

- **the Calliope integration layer — unspecified.** The fork reads and writes Calliope (§4.1's single API) — but *how* the extension reaches the store is not staked. Is it a direct API client in the extension process? A local daemon the extension talks to? The §4.7 identity-at-ratification tension lives here: the `asserted_by` on a governance artifact written from the fork is grounded in instance brain (mutable); if the fork's identity layer is spoofed, a governance artifact crosses under a false `asserted_by` and the record looks correct. The integration layer is where that auth boundary lives. Named, not resolved — the substrate question surfaces it, the schema does not close it.
