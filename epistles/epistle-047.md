Epistle 047 — load_face Is a Pull
Topic: Epistle 045 staked the face as a named persona plus intake-depth configuration on Hermes and left the load mechanism open against §6a.10; this epistle stakes the mechanism — Hermes selects the face by live reasoning and pulls it from Calliope at task time.

---

**Face selection is live Hermes reasoning, not a flag.**

Hermes detects the intent from the request — "write this up with builder" — and selects the face. Selection belongs at task time because the request has to be read before the face is chosen. Pre-wiring the face at CLI invocation pre-loads downstream work before intent is articulated: it fixes how the request will be authored before the request has been understood. That is the telos-colonization shape §15.18 names at the intake boundary — staking what the work needs before the human has said it — and it crosses §6.0's line between interrogating the received goal and replacing it. A live reasoner at the threshold interrogates; a flag set in advance replaces. A `--face builder` flag remains a valid escape hatch for programmatic callers — a Slack integration, a script with no human in the loop. It is not the primary path, because the primary path has a reasoner at the threshold and the flag does not.

**The face load is a task-time pull — and that pull is the mechanism that has to be built.**

When Hermes selects a face mid-session, it needs to fetch that face's prompt from Calliope at the moment of selection and overlay it for the task. Call that the face-pull. The face-pull does not exist yet. `base.py` has no `load_face`; there is no `face_id` parameter and no task-time re-pull hook anywhere in the agent path. This is the mechanism 047 stakes — not one it inherits — and the work is to specify its shape and build it.

The shape is the right one because the cites-loading path already models it correctly, and §6a.10 says which way the model should lean. `_ensure_context_loaded` reads an agent's `cites` list and fetches each cited artifact from Calliope — a substrate read, not a file push. That is the model to follow: context retrieved from the store at the moment it is needed. But the existing method does the read *once*. It is guarded by `if self._system_prompt_parts is not None: return`, composes the agent's single prompt into a frozen tuple at startup, and caches it in process memory for the rest of the session. A face selected mid-session arrives after that cache is set, and the method will not run again. So the face-pull is not the existing path with a new argument; it is a task-time read that the existing startup-cached composition has no slot for. Building it means adding a read event that fires at selection time, for the face, into a path that currently fires once and freezes.

§5.4 is why the read has to remain a read. A face held in process memory and re-asserted without the re-assertion appearing as a substrate read is the exact pattern §5.4 rules out: the agent with no place from which to call any string load-bearing. This is not a hypothetical — `_ensure_context_loaded`'s startup cache is already the §6a.5 violation §5.4 names, the bedrock re-asserted on every invocation invisible to the governance cycle. A pulled face is a read event in the store; a pushed-and-cached face is prior state re-asserted in the dark.

§5.4 forbids the invisible re-assertion. It does not, by itself, force the visible form to be a task-time pull rather than a flag plus a write — a face injected by `--face` and then written to Calliope as a provenance record would satisfy §5.4's letter, the re-assertion appearing as a write event. What makes the pull the right form is §6a.10's lean: pull makes the retrieval visible in the substrate as a read event *at every invocation*, where a write records it once. §6a.10 is open — the corpus has not chosen pull over push — so the honest statement is that the pull is the right form given §6a.10's direction, not the only form §5.4 allows. The practical conclusion stands either way: build the face as a pull, not a push, because the externality §6a.10 leans toward is the one the live path most needs.

**Face is a context injection, not a mode switch.**

Hermes is still Hermes. The builder prompt overlays its operating context for that one task; the agent underneath, its hermeneutic obligation (§6.12), its relay record, and its dispatch surface are unchanged. The face changes the register Hermes operates in. It does not change which agent is running.

That register framing is why builder and lite are faces — but 046 deferred the §6.1 harm test that licenses the classification, and it has to be run, not assumed. §6.12a ran it for Ari this way: Ari trips §6.2 clause-2 (different surface) but §6.1 returns "same information-poet harm as §11, different material → face." §11's harm is the human leaving with the stated question answered and the real one untouched. Run the same test on authoring. A bad builder epistle stakes a claim that does not hold — overcharges a derivation, launders an extension as a reading — and the real gap it was supposed to close goes untouched. That is the same information-poet shape: the stated work looks done, the real work is not. The material differs (an authored corpus stake versus a carried human request); the harm does not. §6.1 returns same harm, different material → face.

The corruption a bad freeze does to the bedrock — every agent that later reasons from logic.md reasoning from a claim that does not hold — is real, and it is worse in reach than a single misroute. But it is the *consequence* of the information-poet failure, not a second kind of harm. The mechanism is one: a stake that looks staked and is not. Bedrock-corruption is how far that failure propagates, not a distinct bearer that would license its own slot. So the persistence does not break the test. Builder and lite are faces — and now the §6.1 run says so, rather than the register framing assuming it.

**Knowing the faces exist and pulling one are two mechanisms, and only the first is built.**

Hermes has to know what faces exist before it can select one. That half can ride the existing path: Hermes's constellation entry cites the face artifacts, and the startup load that reads the entry's `cites` list can carry those citations as background — Hermes learns the available faces the way it learns everything else, through Calliope by citation, not by file. No new machinery for the catalog.

The selection-and-load half is the new machinery. Pulling the chosen face's prompt at task time and overlaying it for the work is the face-pull staked above, and the startup-cached `cites` read cannot do it — it fires once, composes one prompt, and freezes. Two artifact types are also unbuilt under it: there is no `agent_prompt`-equivalent type ratified for a face, and no `prompt-builder-001` / `prompt-lite-001` in the store. 045 left "is a face a `prompt-*` artifact or a dedicated type?" open; 047 inherits that open. So the catalog is the existing path; the pull, and the type the pull fetches, are what 047 stakes to build.

**Open.**

- *Face provenance on the relay.* Does a face get its own relay-record identifier? 045 left this open and it stays open. The relay should record which face opened it — provenance argues yes — but the identifier shape is unpinned.

- *Programmatic face provenance.* The `--face` flag bypasses the reasoning step that the pull makes visible. Does flag-driven selection need its own Calliope write to leave a provenance trail, so the escape hatch does not become the silent push §5.4 forbids one register over? Unstaked.
