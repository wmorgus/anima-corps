Epistle 012 — Three Debts, One Partition
Topic: Are epistemic, substrate, and spec debt (§8.1, §8.2, §8.4) a complete taxonomy of software problem types? Stake the partition and its principle, and turn the three debts into explicit search buckets for extraction rather than undifferentiated "problems."

**claim.** The three debts are not three arbitrary buckets. One partition. The principle: a software problem is a broken because-link, and there are exactly three links that can break. (1) Intent → code: the code no longer implements the live intent — spec debt (§8.1). (2) Artifact → because: the because was never captured or is lost — epistemic debt (§8.2). (3) Code → world: internal chain intact, external substrate drifted past it — substrate debt (§8.4). Three links because the architecture binds three things: a stated intent, a recorded because, an external referent. A problem is one of these bonds failing. Extends §8 — names the partition principle §8 implies but does not state.

**the partition test.** For any software problem, ask: which because-link broke. The answer is forced and singular per link. Spec debt — is the code coherent against its origin but the origin moved (§8.1)? Epistemic debt — is the because absent, every change unquantifiable risk (§8.2)? Substrate debt — is the internal chain intact but the world it was coherent against gone (§8.4)? The three correctives confirm the cut: supersession addresses spec (§3.10), citation addresses epistemic (§3.11), positional diagnosis addresses substrate (§6.14) — three disciplines, three debts, no discipline serving two debts, no debt unserved. The corrective map is the receipt that the partition is real, not a list.

**exhaustive over the modeled space, not over all software.** Claim bounded. The three debts are exhaustive over what the architecture *models*: a system of artifacts bound by intent, because, and referent. They are not a claim about all possible software pathology. A problem the architecture does not model — performance regression, a wrong algorithm that faithfully implements a correct-but-bad intent, a bug that is neither drift nor missing-because — is not a fourth debt. It is outside the diagnostic posture's frame. The taxonomy is complete relative to §8's question (what kind of debt has accreted), not relative to "what can go wrong with software." State the bound or the claim overreaches.

**the fourth thing §8.5 names is not a fourth debt.** §8.5 names a thin artifact chain — agents cannot reason from an underdeveloped record — as a runtime fault alongside spec and epistemic debt. Resist reading this as debt-type four. A thin chain is not a broken bond; it is too few bonds laid down. Epistemic debt is a because that should exist and is absent (link broke). A thin chain is a because-network never built dense enough to carry. Adjacent, distinct: epistemic debt is a hole in the record, thin chain is a record too sparse to traverse. Both surface as the inverted review/rescue ratio (§8.5), which is why §8.5 lists them together — same signal, different fault. Flag: the line between "missing because" and "too few becauses" may not be crisp at the margin. Held, not resolved.

**Mnemo searches three buckets, not one.** Payoff. The partition converts extraction from "find the problems" into three typed searches. Mnemosyne (§6.13) does archaeology — surfaces what the code argues and where the argument fractured. The fracture is not generic. It is one of three: the code argues a stale intent (spec), the code argues with no recoverable because (epistemic), the code argues against a world that moved (substrate, the §6.14 Pavel boundary). Undifferentiated "problem" hunting under-specifies the search; the agent does not know what shape of fracture it is looking for. Three buckets make the obligation explicit: for each fracture, which because-link broke. This sharpens §6.13's reasoning obligation ("name where the argument fractured without being named as a fracture") — fracture has a type, and the type is the debt.

**the archaeology/diagnosis split falls out of the partition.** §8.3 splits Mnemosyne (archaeology) from Pavel (diagnosis) and §6.13/§6.14 give them different harms. The partition explains the split mechanically. Spec and epistemic debt are internal — they live in the intent→code and artifact→because links, both inside the codebase's own chain. Archaeology reads the internal chain (Mnemosyne). Substrate debt is external — the code→world link — and reading it requires the world of forms, not the codebase alone. Diagnosis reads the external link (Pavel, §6.14, OPEN). The two postures are not two styles; they are the internal-link buckets versus the external-link bucket. §8.3's "diagnosis is not archaeology" is the partition's internal/external seam.

**tensions.**

- *Are the three links orthogonal or ordered — genuinely open.* The partition assumes a clean cut: a problem is exactly one broken link. Real codebases carry compound debt — stale intent (spec) whose because was also never recorded (epistemic). Is that two debts coincident, or one root with two faces? If links can break in causal sequence — missing because → drift unnoticed → spec rot — then "which link broke" has an order, and the singular-answer test (above) is a snapshot that loses the chain. Flag. The buckets survive as search targets either way; the *independence* of the buckets may not.

- *Whether "outside the modeled space" is stable.* The bound (exhaustive over modeled, not over all software) holds only if the model is fixed. If the architecture later binds a fourth thing — say, a performance contract as a first-class referent — a fourth debt-type appears and the partition was never complete, only complete-so-far. Don't know whether the three bonds are the architecture's permanent commitment or its current one. Bounds the exhaustiveness claim to the corpus as it stands.
