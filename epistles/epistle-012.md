Epistle 012 — Four Primitives, One Partition
Topic: Four debt primitives — spec, epistemic, substrate, craft — tile all software problems, not just Mnemo's detection surface. Derive every named debt type (test, performance, security, dependency, documentation, data model, Conway, API) as an explicit composition of the four. Give the Mnemo + Pavel decomposition playbook: any named debt → primitives → posture.

**claim.** Four irreducible primitives tile all software debt. Spec — intent→code alignment broken (§8.1). Epistemic — artifact→because alignment broken (§8.2). Substrate — code→world alignment broken (§8.4). Craft — intrinsic structure degraded: high coupling, low cohesion, accidental complexity. First three are broken alignments. Fourth is not an alignment failure — a quality failure of the artifact itself. Extends §8; supersedes the "exhaustive only over Mnemo's detection surface" bound that an earlier draft of this epistle imposed. The partition is exhaustive over all software, not one posture's surface.

**the partition principle.** Software is an artifact embedded in relationships. A problem lives either in a relationship or in the artifact. The relationships are three — intent, recorded because, external referent — because the architecture binds exactly three things (§1.12 spine: stated intent, the *because* upstream, the running-system referent). A broken bond is spec, epistemic, or substrate. A degraded artifact with every bond intact is craft. No third kind: a problem is relational or intrinsic, and the relational ones are enumerated. That is the exhaustiveness argument.

**falsifiability condition.** Name a software problem that is neither a broken alignment link nor a degraded intrinsic quality. If one exists, the partition is incomplete. Until one is named, four primitives stand as the complete tiling. State the condition explicitly so the claim can die honestly.

**tension with §1.7 — named, not resolved.** §1.7: debt is *always* a failure in the intent chain, not code quality; code-quality remediation addresses none of the three forms. This epistle promotes craft — a code-quality failure — to a fourth primitive. Direct conflict. Two readings. (a) §1.7 defines "debt" narrowly as intent-chain failure, and craft is a real software problem *outside* that definition — then the partition is over "software problems," a superset of §1.7's "debt," and §1.7 stands unrevised. (b) §1.7 overreached by saying *always*, and craft is debt §1.7 excluded by fiat — then §1.7 needs revision. Flag. The decomposition section below works under either reading; the word "debt" is the only thing at stake. Held.

**the posture mapping.** Four primitives fall onto two postures. Spec + epistemic live inside the artifact chain → archaeology reads them → Mnemo (§6.13). Substrate + craft are read by judging the form against the world → diagnosis → Pavel (§6.14, OPEN). Substrate: world moved past the form. Craft: the form is intrinsically ill-shaped. Both are read by looking at the form on the world of forms, not by tracing a snapped internal link. Mnemo and Pavel together tile all four. Neither alone does. §8.3's archaeology/diagnosis seam is the internal-bonds / form-judgment cut.

**craft routes to Pavel — structural unity, not convenience.** Pavel's posture is one instrument: read the code against a known form (§6.14). Substrate and craft are the same posture at different standards. Substrate: the form is the current external world (CAP, CVE landscape, platform supersession — §8.4); read the code against it, name where the world moved past. Craft: the form is the ideal of well-made code (coupling discipline, cohesion, layer integrity, boundary theory); read the code against it, name where the artifact falls short. Same instrument, different referent-standard. Both jobs require knowing the standard. That is why both are Pavel's — not convenience bundling, structural unity. Resolves the earlier open tension that craft was the weakest leg.

**the gap is the corpus, not the posture.** Pavel reasons FROM ur-software corpora (§6.14 domain). Those corpora cover the macro level — what the world of software practice looks like (`application`, `concurrency`, `data`, `distributed`, `security`). They do not yet cover the micro level — what a well-formed module looks like: coupling discipline, cohesion heuristics, abstraction-layer integrity, module-boundary theory. So craft has the right posture but no ground. Pavel can run the substrate standard from corpus; he runs the craft standard from first principles — ungrounded. Dependency, flag: craft routes to Pavel *contingent on* an ur-software corpus covering structural quality (something like `corpora/ur-software/structure.md`). Until that corpus exists, the craft leg is grounded in posture but not in corpus. Epistle 013 stakes what that structural corpus should contain.

**named debts are compositions.** Point of the epistle. Every named debt type is a composition of the four primitives, not a fifth thing. Treated as a monolith, a named debt is intractable — no single corrective fits. Decomposed, each fraction routes to its primitive and its posture. Decomposition is the first diagnostic move.

- *Test debt* = epistemic + craft + spec. Tests are recorded *becauses* for behavior. Missing tests → epistemic (the because is absent). Tests not matching live behavior → spec (referent moved). Brittle, badly structured tests → craft.
- *Performance debt* = substrate + spec + craft + epistemic. Execution environment drifted → substrate. Requirement moved → spec. Algorithm always inefficient → craft. No one knows why it's slow → epistemic.
- *Security debt* = substrate + spec + epistemic + craft. Threat model / CVE landscape changed → substrate. Requirements absent or wrong → spec. No one knows why the pattern was chosen → epistemic. Implementation just bad → craft.
- *Dependency debt* = substrate + epistemic + spec. Substrate primarily (EOL, version drift). No one knows why the version was pinned → epistemic. Dependency no longer satisfies its contract → spec.
- *Documentation debt* = epistemic + spec + craft. Epistemic primarily (the missing because). Docs no longer match behavior → spec. Docs poorly written → craft.
- *Data model debt* = spec + epistemic + craft. Schema no longer maps to domain → spec. Structure unexplainable → epistemic. Design poor → craft.
- *Conway / org debt* = substrate + epistemic + craft. The org is part of the world the code was coherent against → substrate. Ownership rationale lost → epistemic. Boundaries reflect a dead org, now just bad → craft.
- *API / interface debt* = spec + craft + epistemic. API no longer serves callers → spec. Design inconsistent or leaky → craft. Shape unexplainable → epistemic.

The pattern: most named debts touch three or four primitives. The name is a surface; the primitives are the structure. Same word ("test debt") hides four distinct corrections.

**the Mnemo + Pavel playbook.** Falls out directly. Any named debt → decompose into primitives → route each primitive to its posture. Spec + epistemic → Mnemo (archaeology, internal links). Substrate + craft → Pavel (diagnosis, world of forms + intrinsic quality). A single named debt is simultaneously Mnemo's and Pavel's problem — the decomposition says which fraction belongs where. Test debt: the epistemic and spec fractions are Mnemo's; the craft fraction is Pavel's. No named debt routes whole to one posture. This sharpens §6.13's reasoning obligation: "name where the argument fractured" gets a typed answer, and the type names the posture.

**§8.5's fourth thing is still not a fourth primitive.** §8.5 names a thin artifact chain — too few bonds laid down — alongside spec and epistemic debt. Not a fifth primitive. A thin chain is not a broken bond and not a degraded form; it is a because-network never built dense enough to carry. Epistemic debt is a hole in the record; thin chain is a record too sparse to traverse. Adjacent, distinct. Both surface as the inverted review/rescue ratio (§8.5). Flag: the margin between "missing because" and "too few becauses" may not be crisp. Held.

**tensions.**

- *Compound debt — orthogonal or ordered.* The decompositions list primitives a named debt *can* touch; real instances carry several at once, and possibly in causal sequence — missing because (epistemic) → drift unnoticed → spec rot → bad patch (craft). Is that four coincident primitives or one root with four faces? The decomposition survives as a search checklist either way; primitive *independence* may not. Flag.

- *Whether four is permanent or current.* The partition is exhaustive against the falsifiability condition as it stands. If the architecture later binds a fourth relationship as first-class (a performance contract as a standalone referent), a fifth primitive appears and the tiling was complete-so-far, not complete. Don't know if four bonds-and-quality is the architecture's permanent commitment. Bounds the claim to the corpus as it stands, not to all possible software.
