Epistle 045 — The Face Is Configuration, Not an Agent
Topic: §6.12a stakes Ari as the face Anima wears in the dojo, not a constellation entry. This epistle derives the face/agent distinction from §6.12a and then extends it: a face is a named persona plus an intake-depth configuration on Hermes, and any host context can configure one. The extension is new construction on the amendment track, not a reading of frozen §6.12a. Its consequence is that Hermes's intake depth becomes configurable, and Option B (Hermes absorbs intake) follows as the only reading consistent with §6.12a and this extension together.

---

**The face concept generalizes; Ari is one instance.**

§6.12a is explicit: Ari is a FACE, not a constellation entry — the persona the system wears in the dojo before the relay chain engages. The load-bearing word is *face*. Ari is the dojo's instance of it: a name (*phronesis*), a cultivation-specific intake posture, Hermes underneath. §6.12b confirms the shape — the dojo face and the orchestration authority are "two expressions of one telos authority," not two agents. The face is a register Hermes operates in, not a being that operates Hermes.

Once the face is named as a configuration rather than an agent, the same three parts can be fitted to any surface. A Slack-based CL assistant would be the face Anima wears in that context: a named persona, a configured intake posture, and Hermes carrying the request underneath — Ari's three parts on a different surface.

State the load-bearing distinction plainly. §6.12a stakes the face/agent *distinction* on exactly one surface — Ari, the face the system wears in the dojo. This epistle extends that distinction to arbitrary host contexts: any host can configure a face. That extension is new construction. It is not a reading of §6.12a; §6.12a names one face on one surface and stops there. The universal quantifier — *any* host, *a* face — is added here, built on top of §6.12a, and it belongs on the amendment track, not in §6.12a as already-committed. The face/agent distinction is derived from §6.12a; the generalization is an extension of it. Keeping those two straight is what keeps this epistle from the founder-exemption move §3.3a names — reframing a new extension as clarification of frozen material.

**Intake depth is a Hermes configuration.**

The current CLI goes straight to `HermesAgent.run(task)`. That is Hermes at shallow intake depth — the task arrives already formed, Hermes routes it. The dojo runs Hermes at a different depth: Ari holds the conversation, cultivates the because-chain, clears the human only at telos-readiness (§6.12a). Same agent, same hermeneutic obligation (§6.12 — carry meaning across the boundary without distortion), different depth at which meaning gets carried.

Intake depth is therefore the configurable axis. The corpus already evidences two settings:

- *Shallow* — the default CLI. The task arrives formed; Hermes routes.
- *Cultivating* — the dojo. Hermes holds the conversation at depth before routing, surfaces the because-chain. This is Ari.

A face on an external host does not add a third value to this axis. It is one of these two settings — cultivating or shallow, depending on the face's purpose — applied to a new surface. The new thing a face contributes is the surface (the generalization above), not a new depth. A Slack face that holds the conversation before routing is the cultivating setting on Slack; one that takes formed requests is the shallow setting on Slack. The axis has two values; the extension lets those two values run on surfaces beyond the CLI and the dojo.

A face is system-prompt-level persona plus an intake-depth setting. The host invokes `anima --face socrates` (or equivalent config); Hermes loads the face's persona and intake depth from a Calliope `prompt-*` artifact. No new agent class is introduced, because none is needed — the intake capability was always Hermes's, and the face is the configuration that selects how deep it runs.

**Option B is forced, not chosen.**

Pulling intake into the CLI as a separate mode — a distinct intake agent the CLI invokes alongside Hermes — re-introduces the exact face/agent confusion §6.12a was written to resolve. If "the dojo has cultivation" became "there is a cultivation agent," the corpus would carry a constellation entry §6.12a explicitly ruled out.

The §5.1 argument is what forces the conclusion, and it runs through the extension, not around it. §5.1 rules out mesh: peer-to-peer agent messaging, agents talking to each other instead of through the store. Per-host intake agents would be exactly that mesh — every host breeding its own intake agent, the faces reassembling the peer-to-peer topology §5.1 forbids, one face at a time. But that consequence only bites *if* faces generalize to arbitrary hosts. If the extension weren't staked — if faces lived only in the dojo — there would be no proliferation for §5.1 to rule out, and a separate dojo intake agent would face only the §6.12a face/agent objection, not the mesh one. So the force is conjunctive.

Option B — Hermes absorbs intake, intake depth is a configuration on the one front door — is the only reading consistent with §6.12a **and the extension this epistle stakes**. Not §6.12a alone: §6.12a alone rules out a *dojo* cultivation agent; it is the extension that turns a local rule-out into a general one. Charging the whole result to frozen §6.12a would overcharge the conclusion to the frozen section while the load is carried by the new construction. Stated honestly, Option B is downstream of the extension — which is the correct shape: the configurable-axis premise produces the configurable-axis conclusion. Ari as a dojo face does not mean "dojo-only intake capability." It means the dojo has a named face whose intake depth is set to cultivating. The intake capability is Hermes's; the face is the name and persona and depth-setting for one context. This mirrors Bench's own shape — "CLI is the spine; UI is a face on it" — at the intake layer: Hermes is the spine, the face is a configuration rendered on it, never a replacement for it. The Bench mirror reinforces Option B; it does not independently establish it, since it inherits the same extension premise.

**The sock puppet is the honest form.**

A face is a sock puppet: transparently a face. Anima does not hide that it is Anima — it wears a character fitted to the context. This is honest under §1.5 (do not import obligations you do not owe). A face that pretended to be a human would import the social obligations of a person Anima is not; a face that is openly Anima-in-a-persona imports none. The persona is a register, declared, not a disguise. The constraint also runs through §9.4: a face that concealed it was Anima would be the silent move §9.4 rules out — the system pretending not to know what it knows. Surfacing what you are is not optional politeness; it is the same honesty constraint, read at the persona layer.

The face name and persona should fit the host's culture, not be prescribed by the corpus. Socrates is a directional example for a CL Slack context, character to be decided by the people whose culture it joins. The corpus stakes the mechanism — named persona plus intake depth on Hermes — and stops there; which character fits CL's Slack is a human call, not a corpus claim.

Socrates as the example name is not arbitrary. §6.12 records that "Socrates" was tried as a name for Hermes and superseded — Socrates teaches within a tradition, Hermes carries meaning across traditions, and the function was evicted from the front-door agent. The teaching register evicted from Hermes-the-agent is a register a face could wear, and Socrates's history illustrates the face/agent distinction tidily. Read this as illustration, not architecture. The distinction is carried by the §6.1 mechanism in §6.12a, and §6.12a already re-homed the evicted cultivation function to Ari — so the name-recycling demonstrates nothing the mechanism does not already carry. It decorates the distinction; it does not establish it.

**Open.**

- *Face identity's home.* Is a face a `prompt-*` artifact, or does it need a dedicated Calliope type? A face carries persona, intake depth, and likely a relay-provenance handle — that may exceed what a prompt artifact holds. The shape of the configuration determines the type; the shape is not yet pinned.

- *Load mechanism.* How does Hermes acquire a face at invocation — config flag, environment variable, or a Calliope query at startup? The instinct is to pull from Calliope, not have the caller push the face in, and the warrant is §5.4 / §6a.10. §6a.10 is the live pull-vs-push surface: pull respects the externality requirement at every invocation and makes the retrieval visible in the substrate as a read event; push collapses both. §5.4 sharpens it — a face config held in process memory and re-asserted without that re-assertion appearing in the substrate is the exact pattern §5.4 names, the agent with no place from which to call any string load-bearing. A pushed-in face is cached prior state; a pulled face is a substrate read. The instinct is right; the corpus has not staked it, and §6a.10 is the open it belongs to.

- *Face provenance on the relay.* Does a face get its own relay-record identifier? The relay should know which face opened it — provenance argues yes. Unstaked, but leaning.

- *Status against §6.12a.* The face/agent distinction is §6.12a's and is derived from it. The generalization to arbitrary host contexts and the intake-depth axis as a named configurable parameter are new — they extend §6.12a without contradicting it, and they belong on the amendment track, not in §6.12a as already-committed. This epistle stakes them as an explicit proposed extension, not as a reading of frozen material. Whether the extension freezes as a §6.12a amendment is the call shitcorping rules on; what is settled here is that it is extension, not derivation.
